# 直播事件规范 v1

[English](EVENTS.en.md) · [测试与回放](TESTING.md) · [JSON Schema](../schemas/live-event.v1.schema.json)

适用：LiveConnect 0.7.2；事件 `schemaVersion` 仍为 **1**。主页/粉丝数快照属于独立模块，不是直播互动事件。四平台为 `bilibili`、`douyin`、`kuaishou`、`wechat`；小红书不包含直播采集。

可选 `user_badges` 最多 16 项，每项为 `{kind, label, level?}`；`kind` 为 `role`、`membership`、`fans`、`wealth`、`level` 或 `title`，标签最多 64 字符，等级为 1–1000 的整数。缺失保持缺失，旧 `badge_name` / `badge_level` 继续兼容。头衔只属于当前消息发送者，不可跨用户／房间缓存，不作为权限或当前成员身份依据。仅识别明确字段和已核对的资源标识，不分发平台图片或猜测未知图片含义。

## 输入、输出与兼容

采集器的原始事件交给对应 `room.ingest(raw)`；Java 的 `{kind:'event', event:raw}` 须先解包。输出为冻结的标准对象；重复返回 `null`，无效输入抛错。不要把已经标准化的事件再送回 `ingest`，否则标识会被再次包装。

Schema 校验标准化输出，不是原始协议输入，也不是脱敏器。它检查公开字段结构、必要字段和计数模式；允许未来增加可选字段。协议来源是否可靠、路由是否正确、礼物金额语义等仍由采集器、核心和消费端联合保证。未知字段不能直接渲染为 HTML 或公开输出。

| 字段 | 合同 |
| --- | --- |
| `schemaVersion` | 当前为 1；破坏性字段/语义变化须升级合同版本。产品版本独立使用三段数字。 |
| `event_id` | `live:<platform>:<encoded room>:<encoded source ID>`；模拟低层输出用 `preview:`。原始有效 `event_id` 优先于 `source_msg_id`，均缺失/无效则生成 UUID。 |
| `source_msg_id` | 平台原始编号或空串；字符串保留精度，数字只接受安全整数，不按文本或昵称去重。 |
| `platform` / `room_id` | 会话绑定的实际路由，输入中的同名字段不能覆盖。房间/用户标识为不透明字符串。 |
| `sequence` | stream/订阅输出中的本实例接收序号；低层 `normalizeEvent()` 没有此字段，不是平台全局序号。 |
| `timestamp` / `received_at` | 毫秒；前者保留有效输入时间，否则回退本机时间；后者为接收时间。不是跨平台同步时钟。 |
| `source` / `preview` | 来源标签与模拟标志；`openRoom` 拒绝 `preview:true`。离线回放在外层报告明确标记 `synthetic:true`，不会谎称连接了平台。 |
| `user_id` / `user_name` | 缺失 ID 为空串，缺失昵称为“一位朋友”；昵称不能作为身份或去重键。 |
| `count` / `count_mode` | 增量、快照或信号，必须分别处理，见下表。 |
| `value` | 当前为 null，不表示人民币价值。 |

完整可选字段、头像/表情、PK 与可见名单结构见 [API](API.md) 和 Schema。精确长整数、PK 比分和价格字符串不得转成浮点数；缺失不等于零。

## 事件语义

| 类型 | 消费规则 |
| --- | --- |
| `comment` | 文本弹幕；将 content 当作文本，不执行其中的 HTML。 |
| `gift` | `count === gift_count`，本条礼物增量 1–1000000。原始连击总量由适配器处理，不在消费端重复累加。 |
| `like` | Java 平台已知增量；视频号为 `signal`，表示动作发生，不能把 count=1 当作精确新增一赞。 |
| `enter` / `follow` / `share` | 仅表示适配器有协议依据的动作，不从人数/昵称变化推断。 |
| `notice` / `entry_effect` | 通知与入场特效，不自动等同关注、普通进房或付费礼物。 |
| `super_chat` | B站醒目留言及其已知 ID/原始金额。 |
| `super_chat_delete` | B站撤回 ID 列表；删除相应展示或持久记录，不新增互动计数。 |
| `room_stats` | `snapshot`、count=0；当前观看/累计观看/累计点赞分开处理，不相加。未知字段省略，显式 0 保留。 |
| `viewer_snapshot` | `snapshot`、count=0；可见名单/贡献榜片段不等于完整在线名单，不派生进场、离场或停留时长。 |
| `pk_status` | `snapshot`、count=0；只使用具有协议依据的场次、双方和分数，不推断未知胜负。 |
| `live_status` | 平台直播状态与采集器连接状态分开；断线不意味着主播已下播。 |

核心中的 `delta` 标签不等于所有事件都应加到业务计数器；必须同时判断事件类型。礼物原始金额还须按平台/单位解释，不能统一乘数量或跨平台换算收入。

## 去重、顺序与房间生命周期

- 去重按核心生成的事件 ID，在平台和房间间隔离；窗口为接收后 **10 分钟**（严格超过 600000 ms 后失效），容量最多 **20000** 个 ID。容量驱逐、时间到期、进程重启或房间关闭后，旧事件可再次被接受。
- 相同 ID 的重投返回 null，不递增 sequence、不重触发礼物。没有可靠 ID 的消息使用新 UUID，无法据此保证重投去重。
- 输出保持**接收顺序**，不按 timestamp 排序；迟到事件有更大的 sequence 和更早的 timestamp。需要时间窗口的应用须定义自己的迟到策略，不能声称已经恢复上游断网期间丢失的数据。
- 重连若保留原房间对象，可保留其去重状态；`close()` 会清除该房间去重/历史/头像缓存。新建同一路由不会继承去重。旧对象关闭后调用 ingest 会抛错。
- 切房必须按事件真实来源路由。旧房间的迟到真实互动可继续存入旧房间历史，但不能清空或改写当前房间统计；关闭旧会话后拒收其回调。不能将“当前 UI 房间”当作所有回调的归属。
- 历史共保留 100 条，不是每房间 100 条。三类快照和撤回不作为可重播动作存入历史；撤回还会移除对应醒目留言。订阅不自动重放历史。
- 头像补全是元数据更新，不能再加计数或重放礼物。订阅回调失败相互隔离，异步回调不被等待；有界业务队列、持久化和跨重启幂等由宿主管理。

## 开源数据边界

新增 fixtures 全部独立手写/生成，只使用 synthetic 标识，不读取主播端、登录状态、观众记录或真实直播采样。公开测试不需要 FurryUP 账户。Schema 或 synthetic 标签本身不能证明任意外部数据已脱敏；贡献者必须审查数据来源，不能将真实抓包换个文件名后提交。抠图、模型资源、主播端私有模块不在此次范围内。
